这篇文章来解决“服务失败了，如何判断是哪里出了问题”。

一个服务启动成功了，这是好事，我们可以不用继续优化他。但是如果一个服务启动失败了，我们需要有能找到问题的能力。**异常处理**就是用来辅助我们快速定位问题的。

java 当中有很多种异常，但是我们可以简单地将它们划分为两类：请求没有到达上游（`ResourceAccessException`)和请求到了但是返回了错误（`RestClientResponseException`）。

java 当中出现的异常，会**一层一层地往上冒**。什么意思呢？举个例子：假设 A 方法调用了 B 方法，B 方法调用了 C 方法，而 C 方法又调用了 D 方法。这时， D 方法出现了一个异常，一般会称之为“**抛出异常**”，如果一直没有人管（后面会讲怎么样才是“管”一个异常）这个异常，它就会先到 C ，再浮到 B ，然后到 A ，最后被 Spring 接住。这就是往上冒的过程。

接下来再说明一下**如何“管”一个异常**。java 当中会使用 `try{...} catch(Exception e){...}` 。try 的里面是一些业务逻辑，并且是可能会出现异常的业务逻辑，比如调用 GSV 接口，可能会连不上。catch 就是负责管异常的，当有一个异常被抛出，catch 就可以抓住它，如果是 catch 所负责的那一种异常（一个 catch 一般负责一种异常），则会执行后面的处理 。

了解了这些，我们就可以开始对整个项目的异常进行处理。

我的思路很简单：**对所有的异常进行归一化，然后再全部交给 Spring ，让管家按我的要求帮我处理这些异常**。

所谓**归一化**，就是不管出现什么异常，我都把它转化为相同的格式，方便我管理。于是我们就可以新建一个类，用来描述归一化后的异常：
```java
public class UpstreamException extends RuntimeException {

	private final String service; // 变量（字段）：哪个服务出的问题，比如 "GSV"
	private final HttpStatus status; // 变量（字段）：要返回给调用方的状态码

	// 构造方法：cause 是原来那个异常，保留下来方便以后查原因
	public UpstreamException(String service, HttpStatus status, String message, Throwable cause) {
		super(message, cause);
		this.service = service;
		this.status = status;
	}

	// 方法：读取字段
	public String getService() {
		return service;
	}

	// 方法：读取字段
	public HttpStatus getStatus() {
		return status;
	}
}
```

然后，使用 `try{...} catch(Exception e){...}` ，把抓到的所有异常转化为 `UpstreamException` ，也就是新建了一个 `UpstreamException` 对象：
```java
try {
        // 这些是业务逻辑
		return restClient.get()
		.uri(uriBuilder -> uriBuilder
		.path("/tts")
		.queryParam("text", "{text}")
		.queryParam("text_lang", "zh")
		.queryParam("ref_audio_path", "{ref}")
		.queryParam("prompt_lang", ref.lang())
		.queryParam("prompt_text", "{prompt}")
		.build(text, ref.path(), ref.text()))
		.retrieve()
		.body(byte[].class);
	} 
// 抓连接失败的异常
catch (ResourceAccessException e) {
	// 抛出我们自己建立的 UpstreamException
	throw new UpstreamException("GSV", HttpStatus.SERVICE_UNAVAILABLE,
	"连不上 GSV（" + baseUrl + "），它可能没启动或已经退出，请看 gsv.log", e);
	
} 
// 抓返回错误的异常
catch (RestClientResponseException e) {
	// 抛出我们自己建立的 UpstreamException
	throw new UpstreamException("GSV", HttpStatus.BAD_GATEWAY,
		"GSV 返回了错误 " + e.getStatusCode().value() + "：" +  e.getResponseBodyAsString(), e);

}
```

交给 Spring 这个步骤很简单，那就是不写 `try{...} catch(UpstreamException e){...}` 来抓 UpstreamException 。让这个异常一直冒到 Spring 那里。

最后我们需要创建一个类，在这个类的一个方法中，贴上 `@ExceptionHandler(UpstreamException.class)` 这个标签，就可以专门管理 `UpstreamException` 异常，然后在方法中，处理这个异常。
```
// 类：统一处理所有 Controller 里冒出来的异常

@RestControllerAdvice
public class ApiExceptionHandler {

	// 方法：专门接住 UpstreamException
	@ExceptionHandler(UpstreamException.class)
	public ResponseEntity<Map<String, String>> handleUpstream(UpstreamException e)
	{
		// 接住之后怎么处理：
		return ResponseEntity.status(e.getStatus())
		
			.body(Map.of(
			"service", e.getService(), // 哪个服务
			"message", e.getMessage())); // 出了什么问题
	
	}

}
```

再来回顾一下异常从出现到被处理的过程。首先就是出现了一个异常，假设是是在 TtsService 里面，出现了 ResourceAccessException 这个异常。它会被抓住，被归一化为 UpstreamException ，假设处理之后创建的对象是 e 。接着，因为路上没有东西会抓住这个异常，因此它会上浮到 Spring 。Spring 发现它之后，就回去找标签，看看哪个方法是管这个异常的。发现是 ApiExceptionHandler 里面的 handleUpstream 方法管，于是就会新建一个 ApiExceptionHandler 对象，调用 handleUpstream 方法，并把 e 作为参数传进去处理。
