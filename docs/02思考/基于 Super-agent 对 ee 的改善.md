今天读完了 deepseek 发布的《[Super-agent 设计探索：迈向更自主的 Agent 系统](https://www.bilibili.com/opus/1265361021143351318?spm_id_from=333.1007.0.0)》，既发现了与 ee 类似的架构，也大概清楚 v2 该怎么开发。


## Super-agent 架构与 ee 架构的简单对比
---
### 整体框架

官方给出的架构图：
![[09附件/DM_20261101154059_001.png]]

这个架构和目前有的 agent-team 很类似，但不同之处在于，agent-team 的主 agent 是需要深入了解项目细节，从而进行下一步决策，也就是需要进行一定的推理。而 Super-agent 的 Router 层只负责与用户的交互，不再深入了解当前的开发细节，甚至没有执行 bash 命令的权限。任务的推进，极大部分交给了 Worker 层。

我的 ee 中也有类似的分工。[[02思考/关于 AI 管家和陪伴机器人的记忆#^44af1a|在 ee 中，主对话只负责和用户进行聊天。查资料、运输信息和对记忆的加工，它都不干。它做的事情只有一个，和我对话]]。主对话相当于 Router 层，[[02思考/关于 AI 管家和陪伴机器人的记忆#^9bbb42|传输层]]、[[02思考/关于 AI 管家和陪伴机器人的记忆#^72722f|记忆处理层]]则是根据我的需求，固定下来的两个 Worker 层。


### 上下文注入

Super-agnet 关于每个 Worker Session 的上下文注入借鉴了计算机系统设计中经典的**局部性（Locality）** 思想。优先注入最小的信息（如这个 Session 的 ID）和近期最可能用到的信息。

ee 中，每一次主对话都会注入两个东西，一个是 user.md ，另一个是“近况.md”。


## 启发
---
### 云端

ee 目前只能在本地电脑运行，因为需要在特定的目录下使用 agent 开启新对话，这个对话才会是主对话。也就是**环境事件**局限在了本地文件夹。后续我打算部署在云端，然后尝试实现，手机对话。这样更加地接近日常使用。


### 上下文注入的优化

后续的上下文，我打算合并 user.md 和“近况.md”。我打算采用动态调整的方式处理近况的内容：最近几天的放原文，稍微远一点的，就放摘要。每一天对话沉淀之后，都要写一个摘要。做这个的目的：一个是让这个上下文更全面地反馈我的现状，另一个是确保上下文不是很长。


### 全云端

要让 Super-agent 做到持久在线并灵活接入各类真实工作环境，要借鉴计算机系统中**存算分离（Compute-Storage Separation）** 的思想。（Session 数据库是怎么实现的呢？）
![[09附件/DM_20261101161043_001.png]]

基于这个思想，后续我打算对 ee 也做一些处理。最开始我是想存在本地，算在云端。但是这就有一个问题：算的时候需要用到存储的信息，如果我存在本地，该怎么拿到资料呢？于是我思考：为什么要存在本地？我最初设计的时候，是打算看看这里存了什么。但是实际这么长时间的体验，我只会去看每天的计划。所以我现在决定直接存储也放在云端。


### 期望

后续就是，在服务器里，存储着我的信息，以及 24h 运行着主对话。当我通过手机向主对话发信息的时候，服务器的主对话就开始工作。我的信息就一点一点沉淀在服务器中，每隔一段时间，备份在 github 仓库里。ee 的开发可以在本机，也可以在服务器中。
